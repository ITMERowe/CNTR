# CNTR 0.1: fixes, light mode, Indonesian, security review

Status: design, not started. Version stays `0.1.<build>` (1.0 is reserved for the release that ships).

## Intent

0.1 is meant to be a big update on top of the tutorial and sound work: fix the three remaining data and display bugs, let people use the app in a light theme and in Indonesian (the owner's main market sells in IDR, at Indonesian events), and make sure neither the repository nor the app exposes anything it should not before more people install it.

## Goals

1. Deleting a product never deletes a sale.
2. Cancelling an edit of a past event can never end up saving it.
3. An empty day card does not show a misleading date.
4. A light theme, switchable with the current dark theme.
5. The whole app in English and Bahasa Indonesia.
6. A security review of the repository (including git history) and of the app, reported to the owner.

## Non-goals

- More languages, right-to-left layout, or translating what users typed (product names, event names, expenses).
- Changing number formats: they stay tied to the currency setting, as now.
- Changing the data format, backups, or the sales/report maths.
- New features beyond the list above (stock counts, cash count, discounts stay in "ideas").

## Anti-goals (a failure even if it "works")

- Any change that loses or alters existing sales, events or settings on update.
- Light mode that is hard to read: any text below 4.5:1 (tile text keeps the owner's 2.6:1 rule).
- A half-translated screen: English and Indonesian words mixed on the same screen.
- Security fixes applied without the owner seeing the report first.

## 1. Bug fixes

### 1a. Deleting a product keeps its sales (owner decided)
- `deleteProduct()` (`src/state.ts`) stops filtering `state.sales`. It removes the product from the counter (`cntrProducts`) and the product list (`cntrProductHistory`) only.
- Its sales, from earlier days and today, stay in the Event screen, History, Compare and CSV under the product's name and price at the time.
- Why: products get renamed or split ("Posters" → "Poster of X"); past sales must never break.
- The delete confirmation text changes to say the sales stay, e.g. *"Delete 'Sticker'? Its sales stay in your reports. To only take it off the Sell tab, use its switch in Products instead."*
- Known side effect, accepted: a new product with the same name as a deleted one shows the old sales under it (products are identified by name).
- Reports must still colour a deleted product's sales (`productColor()` falls back for unknown names today; check it gives a stable colour).
- Test: sell a product on Day 1 and today, delete it, check every sale is still stored and still counted on the Event screen and in CSV.

### 1b. Cancel while saving a past-event edit (builder's call, below)
- Cause: `saveEditing()` awaits the automatic backup, then saves `edited` without checking that the edit was not cancelled meanwhile.
- Fix: while the save is running, Save shows "Saving…" and both Save and Cancel are disabled (Android back does nothing then too). After the backup, the save goes ahead only if that same draft is still open.
- Test: hold the automatic backup open (fake native bridge), press Cancel, check nothing changed.

### 1c. Empty day card date (builder's call)
- Cause: a day with no sales falls back to the event's start (Day 1) or the previous End day time; for a new event that is "now".
- Fix: a day with no sales shows **"No sales yet"** instead of a date. Days with sales keep showing the first sale's date.

## 2. Light mode (owner decided: VS Code Light+ colours)

- Settings → new **Appearance** row: **Phone setting** (default), **Light**, **Dark**. Stored in `cntrSettings` as `theme: 'system' | 'light' | 'dark'`; old settings without it get `'system'`.
- "Phone setting" follows `prefers-color-scheme`, and switches live if the phone changes.
- Colours: the counterpart of today's Dark+ palette, VS Code **Light+**: background `#ffffff`, panels `#f3f3f3`, raised surfaces in the `#e8e8e8`–`#e4e6f1` range, text near-black (`#1e1e1e` / `#3b3b3b`), lines as dark-on-light alphas. Exact values are the builder's, as long as every text/surface pair is ≥ 4.5:1.
- Implementation shape: the `:root` tokens in `src/style.css` get a light set (e.g. `:root[data-theme="light"]`, plus the `prefers-color-scheme` case for "Phone setting"). The ~44 colour literals outside `:root` are moved onto tokens or given light values. `<meta name="theme-color">` and `color-scheme` follow the theme.
- Product tiles keep their own colours in both themes; the tile text rule (white unless below 2.6:1) is unchanged.
- Money colours (`--positive`, `--negative`) and the 5 payment-method colours must be re-checked on the light surfaces (dataviz validator) and get light variants if they fail; always still shown with the method's name.
- The tutorial's spotlight dim, the bubble, toasts and sheets get light versions.
- Tests: the layout suite's contrast checks run in both themes.

## 3. Indonesian (owner decided)

- Languages: English (default) and Bahasa Indonesia.
- Fresh install: Indonesian if the phone's language is Indonesian (`navigator.language` starting with `id`), otherwise English. Saved in `cntrSettings` as `language: 'en' | 'id'`.
- Existing users updating (owner decided): **English**, whatever the phone's language, until they choose Indonesian in Settings. Detection only runs on a fresh install. Builder must tell the two apart reliably, e.g. "no language saved yet but data or `cntrMeta.tutorialOffered` already exists" means an update.
- Settings → **Language**: English / Bahasa Indonesia. Once chosen it stays, even if the phone's language changes.
- Everything the app writes is translated: static screens (`index.html`), Preact views, toasts and dialogs, the welcome offer, all 28 tutorial steps, the practice data's names, empty states, About and Privacy text, the default event name ("Event <date>" → "Acara <date>").
- Not translated: what the user typed; **payment method names** (Cash, QRIS, Transfer, Card, E-wallet stay English everywhere, owner decided); **CSV column headers** (stay English so spreadsheets and formulas keep working, owner decided).
- Dates: month names follow the **app's** language, not the phone's (`formatDay`, `formatWhen` and any other `toLocale*` call get the app locale). Number formats stay tied to the currency, as now.
- Implementation shape (builder's): one small dictionary module (`en` and `id` objects with the same keys, a `t(key, params)` function); static markup marked with `data-i18n` keys and filled at startup and on language change; TypeScript should fail the build if a key is missing from either language. No i18n library unless it is clearly smaller.
- Indonesian copy is written by the builder in plain, natural Indonesian (the same tone as the English: short, direct); the owner reviews it on the phone.
- Tests: switch to Indonesian and check no English UI text is left on each screen (except user data and brand names); dates show Indonesian months; fresh-install detection picks `id` for an `id-ID` browser and `en` otherwise.

## 4. Security review (report first)

Read-only first; a written report goes to the owner, ranked, and fixes are applied only after the owner agrees.

- **Repository**, working tree and the full git history (all branches): API keys, tokens, passwords, keystores (`*.jks`, `*.keystore`), `google-services.json`, `.env` files, signing passwords in Gradle files, personal data. Check `.gitignore` covers the signing folder and local files. Check that the 3 GitHub secrets are only used in the workflow, never printed in logs, and that workflows from forks/PRs cannot read them.
- **App**: Android manifest (exported components, `allowBackup` / Auto Backup behaviour for the SQLite file, cleartext traffic, the INTERNET permission), WebView settings, Capacitor config (no dev `server.url` shipped), Content-Security-Policy, any `innerHTML` with user data (XSS through product or event names), the restore path against a hostile backup file (size, deep nesting, huge strings), CSV injection in exported files (cells starting with `=`, `+`, `-`, `@`), file paths for exports, and `npm audit` for known-vulnerable dependencies.
- Output: a short report (what was checked, what was found, how serious, the suggested fix).

## Order of work

1. Security review → report → owner decides on fixes.
2. Bug fixes 1a–1c (small, protect data).
3. Light mode.
4. Indonesian (last, so it translates the final text of everything above).

Each step ends with all tests passing and HANDOFF updated; the owner tests 0.1.x on the phone after steps 2 and 4.

## Constraints

- Offline, no new network use; no new runtime dependency unless clearly smaller than writing it.
- Must keep working on the phone's SQLite store and in the browser; old data and backups load unchanged.
- Settings order stays as decided (new rows join existing groups: Appearance and Language in a group near the top of the non-product settings; exact placement is the builder's).

## Calls made by the builder (owner to check)

- 1b: Save/Cancel are disabled with "Saving…" during the backup (instead of making Cancel abort the save).
- 1c: an empty day shows "No sales yet".
- Theme default is "Phone setting"; a three-way choice in Settings.
- Language: Settings offers only the two languages (no "Phone setting" option); the choice sticks.
- Dates use the app's language for month names; English uses day-month-year ("27 Oct 2026").
- CSV *values* the app writes itself (e.g. the default event name) follow the stored data, not the app language, since headers stay English.
